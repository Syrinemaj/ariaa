# 11 — Difficultés techniques, corrections et écarts constatés

Ce document distingue deux catégories, à ne pas mélanger dans le rapport :
- **A. Difficultés réellement documentées dans le code source** (commentaires explicites décrivant un bug passé et sa correction) ;
- **B. Écarts constatés par cet audit entre le dépôt réel et un document antérieur du projet** (`rapport/chapitre_realisation.md`), qui doivent être tranchés par le développeur avant la rédaction finale.

## A. Difficultés documentées dans le code (confirmées par lecture directe)

1. **Faux endpoint fabriqué à partir d'un segment de version** — `app/normalization/dynamic_segment_detector.py`. Commentaire littéral : *« was caught empirically: an early version of this module collapsed exactly that shape into a fabricated "/api/v1/{v1_id}" endpoint »*. Corrigé par l'exclusion explicite des positions suivant un segment de version/environnement connu.
2. **Faux positifs du score heuristique de nettoyage HAR** — `app/ingestion/heuristic_filter.py`. Docstring détaillant la mesure avant/après recalibration contre `evaluation/golden_dataset/traffic_classification_golden_dataset.json` (précision 0.643 → 0.667, F1 0.783 → 0.800). Reproductible via `evaluation/run_scripts/run_traffic_classification_eval.py`. **Seul point de ce type entièrement vérifiable** (contrairement au point B.1 ci-dessous).
3. **Hachage d'idempotence incluant des champs volatils** — `app/idempotency/key_generator.py`. Commentaire explicite : l'ancienne version hachait la ligne complète (timestamps, IDs internes inclus), empêchant toute déduplication réelle. Corrigée pour ne hacher que les champs métier stables.
4. **Secret transmis en clair dans les arguments d'une tâche Celery** — décrit dans un document antérieur comme corrigé par un déchiffrement limité au worker (`app/connections/crypto.py`) ; la trace littérale de ce correctif précis dans le code (commentaire équivalent à celui des points 1–3) n'a pas été retrouvée dans ce passage d'audit — **à reconfirmer par une relecture directe de `app/connections/service.py::get_decrypted_secret_for_execution`** avant de le citer comme « documenté dans le code » au même niveau de certitude que les points 1–3.
5. **Champ `WorkflowModel.confidence_score` inexistant** — `app/planner/plan_builder.py`, commentaires `ARIA-WORKFLOW-V2: Phase 4`, confirmant que le champ prévu par une spécification antérieure n'existe pas réellement dans le modèle (`alembic/versions/013_workflow_entity_action_org.py`) et a été corrigé en `.confidence`.
6. **Verrou distribué contre la double exécution d'un même fichier bulk** — `app/api/bulk.py`, commentaire `BUG-001: distributed lock — prevent double-execution on the same file`, confirmant un bug identifié puis corrigé par un verrou distribué. Détail exact du mécanisme non relu plus loin dans ce passage — **à compléter si nécessaire**.

## B. Écarts constatés entre `rapport/chapitre_realisation.md` et le code réel

Ces points sont du ressort du développeur : soit le chapitre doit être corrigé, soit le code a évolué depuis sa rédaction et il faut vérifier la version exacte du dépôt utilisée.

1. **CRITIQUE — Tableau de comparaison des modèles d'embedding (§4.3.3 du chapitre) non traçable au code.** Aucun script, notebook ou fichier de résultat correspondant à une évaluation Recall@1/MRR sur Cohere/Titan/BGE (12 endpoints, 17 requêtes) n'existe dans `evaluation/`. Les 10 harnais d'évaluation réels du dépôt (`evaluation/README.md`) couvrent exclusivement des tâches de complétion LLM (classification, normalisation, planification...), jamais une comparaison de modèles d'**embedding**. Voir `04_rag_et_recherche_semantique.md` §7 et `09_tests_et_benchmarks.md` §4.
2. **CRITIQUE — L'exécution parallèle par DAG (`dag_executor.py::execute_dag`) décrite comme le mécanisme d'exécution des workflows (§4.8.2–4.8.4 du chapitre) n'est appelée nulle part dans le code applicatif.** Recherche exhaustive (`grep -rl "execute_dag"` sur tout le dépôt) : la seule occurrence hors définition est un commentaire de `dag_builder.py`. À l'inverse, `app/workflows/sequence_builder.py::reorder_steps_sync` — que le chapitre décrit comme « remplacé » et « conservé dans le dépôt mais non utilisé par le chemin d'exécution actuel » — **est réellement appelé en production**, depuis `app/workflows/clustering.py:459`, lors de la construction d'un workflow à partir d'un cluster d'endpoints. Autrement dit, le chapitre antérieur a probablement inversé les rôles des deux modules, ou décrit une fonctionnalité prévue plutôt que celle réellement câblée. **À clarifier avec le développeur avant toute rédaction du chapitre 4.8 : `execute_dag` est-il appelé depuis un chemin non détecté par cet audit (ex. une route API non encore explorée), ou est-ce du code mort ?**
3. **IMPORTANTE — Topologie Celery documentée (5 queues, concurrence différenciée par type de charge) non respectée par le déploiement réel.** `docker-compose.yml` démarre un unique worker écoutant toutes les queues sans la concurrence différenciée documentée dans `celery_app.py` ; `docker-compose.prod.yml` ne spécifie même pas les queues (`--concurrency=4` générique). Aucun service `celery beat` n'existe dans l'un ou l'autre fichier, alors qu'un `beat_schedule` réel programme un nettoyage quotidien (`cleanup_expired_files`). **À vérifier : la tâche planifiée s'exécute-t-elle réellement en production (peut-être via un mécanisme hors de ce dépôt, type cron Azure) ?**
4. **IMPORTANTE — Absence de sanitisation des données sensibles au moment de l'ingestion HAR**, déjà pressentie dans un document antérieur (marquée `[À COMPLÉTER]`) et **confirmée positivement par cet audit** : `sanitize_payload` n'est appelé que lors de la journalisation d'une exécution, jamais lors du parsing/stockage d'un fichier HAR brut. Ce n'est donc plus une incertitude mais un fait vérifié — un fichier HAR contenant des cookies ou données personnelles réelles est conservé tel quel.
5. **IMPORTANTE — Absence de porte de qualité automatisée dans le déploiement.** `infrastructure/github_actions/deploy.yml` construit et déploie directement sur push vers `main`, sans étape d'exécution de tests ou de lint.
6. **FACULTATIVE — Service `otel-collector` référencé par défaut dans la configuration (`OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317`) mais absent des deux fichiers `docker-compose*.yml`.** Les traces OpenTelemetry n'ont donc probablement pas de destination fonctionnelle dans l'environnement tel que défini par ce dépôt, sauf configuration externe non versionnée.
7. **FACULTATIVE — Nom de fichier/fonction résiduel de l'ancienne architecture multi-fournisseur IA** : `app/ingestion/semantic_filter.py::semantic_filter_with_azure` et `tests/unit/test_groq_client.py` subsistent alors que les fournisseurs Groq et Azure OpenAI ont été retirés du code de production (`AI_PROVIDER` fige désormais toujours Bedrock). Dette de nommage sans impact fonctionnel, mais à mentionner si le rapport traite des choix de refactoring.

## C. Limites structurelles confirmées (pas des bugs, des compromis assumés et documentés comme tels dans le code)

- Score de charge utile du nettoyage HAR : correspondance de mot-clé n'importe où dans une valeur aplati, pas seulement comme nom de champ — limite reconnue dans le commentaire de `heuristic_filter.py` lui-même et vérifiable concrètement (`BUSINESS_KEYWORDS` contient `"payment"`/`"payments"`, susceptibles de matcher dans un chemin de maintenance sans rapport).
- `oauth_client_credentials` ne réalise pas d'échange de jeton réel — le secret saisi est utilisé directement comme jeton Bearer, sans renouvellement à expiration (cohérent avec un `auth_type` à 3 valeurs sans logique OAuth distincte observée dans la structure du module `app/connections/`).
- Toutes les politiques d'environnement (`test`/`preprod`/`prod`) démarrent en accès complet par défaut — aucune protection de la production n'est garantie sans configuration explicite (`DEFAULT_ENVIRONMENT_POLICIES`, vérifié littéralement).
- Seuil `PLAN_MIN_RAG_SCORE = 0.3` documenté comme non fiable comme filtre de pertinence cross-domaine — la défense principale contre un mauvais plan reste `PLAN_MIN_INTENT_CONFIDENCE`, pas le score RAG (commentaire explicite de `app/core/config.py`).
